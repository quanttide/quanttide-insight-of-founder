# 引擎与结算

## 1. 问题

引擎要回答的只有一句：在这份命令下，战场上实际发生了什么。它不该知道玩家想做什么，也不该替上层补意图。

## 2. 定义

引擎由三部分组成：世界状态、结算函数、相位。

世界状态持有单位、地形、回合与补给等动态数据。new_game(scenario) 是唯一初始化入口，apply(result) 是唯一写入入口；除此之外没有后台改数据的路径。

结算函数是纯函数：resolve(action, context, rng_stream) 返回 result。随机数只从传入的子流取，回合号与上下文都从参数拿，不读全局状态。

结算次序固定为：机动、接敌、战斗、损耗与补给、撤退与溃散。每一步只返回变更，不直接改世界；变更由 apply 合并写入，变更历史因此可追。

地图与六角格几何属于世界状态，不属于某个结算阶段；放进结算里，机动与战斗会各算一套距离。

## 3. 验证

- 每个机制至少有一个微型想定夹具，手写期望结果；期望结果由人复核。
- 金种子下跑批量对局，统计分布稳定；改动后分布漂移可见。
- 事件流不出现未定义类型；每个事件字段都能在契约里找到定义。
- 引擎包没有界面依赖，也没有浮点。

## 4. 原则

- 引擎越哑，两侧越容易接上；一旦开始推断上层意图，一种玩法就会长出一套结算。
- 数值全部进参数表，代码里不出现裸数值。
- 世界状态只认一个写入口；多一个入口，就多一条绕过关卡的路径。
- 结算函数不判断命令是否合理；合不合法由参谋预检，执行不了由引擎回拒收事件。

## 5. 结论

引擎的价值不在聪明，而在可替换、可复算、可审计。它把真相说清楚，判断留给上层。
