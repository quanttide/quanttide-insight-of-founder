# 契约与分层

指挥部和引擎是两个人写的。一个管判断，一个管结算。只要这两边还要合到一起，中间就得先约定：它们怎么说话。

约定可以很短。指挥部把命令递下去，引擎把发生的事递回来。除此之外，谁也不打听对方的内部。命令长什么样、事件怎么排，可以先定；定完之后，两边都不许绕过这条线去改对方的东西。

问题是，写在纸上的约定不算数。两边都能对着它点头，点头之后各按各的理解写，毛病要等合到一起才暴露。真正算数的，是换桩。

第一版两边都别做真的。引擎收到命令，按写死的规则回一串事件；指挥部把命令摊开，读一遍报告，一个回合就跑完了。这一步不难，难的是下一步：把其中一边换成真实现，另一边一行不改。还能跑，约定就立住了；跑不动，说明约定本身有洞。

这也是为什么引擎要做得笨一点。它只认命令，只说发生了什么。命令该怎么展开、报告该晚多久、敌军当时信了什么，都不归它管。它越笨，两边越容易接上；它一旦开始猜意图，两种玩法就得分家。

笨还要笨到编译器里。事件在关卡处被翻成报告，过了这道关，上层就只拿得到报告。谁想在上层直接碰事件，构建立刻失败。这条规则不靠人记，也不留例外。

最后才是入口。脚本、命令行、界面，换哪个都行。只要它们走同一条命令通道、读同一份报告，换的时候就不用动机制。反过来，如果机制开始跟着界面走，今天加一个按钮、明天改一处结算，最后没人说得清游戏本身变没变。

所以，判断这份约定行不行，不用看它写了多少页。问一句就够了：换掉一边，另一边还要不要改？不用改，它就还在；要改，先改约定，再改实现。
