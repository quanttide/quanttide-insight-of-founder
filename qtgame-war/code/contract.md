# 契约与分层

指挥部与引擎之间，只该有两条通道：命令向上，事件向下。谁在下令、界面长什么样，都不该改变这两条通道的形状。契约要证明的，就是这件事不随两边的实现而变。

证明的办法不是把格式写清，而是换桩。两边的第一版都对着假实现开发：引擎收到命令就按写死的规则回一串事件，指挥部把命令摊开、读出报告，闭环先跑通。然后任选一边换成真实现，另一边一行不改。如果还能跑，契约才算立住；如果跑不动，错在契约，不在实现。2026-10-25 的《系统契约》路线图把阶段 1 的验收压在这一步上。这是全程最便宜的一次验收，也是唯一一次能用改动量说明问题的验收。

换桩能成立，前提是引擎足够哑。它只认命令、只说真相，不知道意图、迷雾和参谋。翻译与认知全留在指挥部侧：一道纵队命令怎么展开、报告怎么延迟与失真、敌军 AI 信了什么，都在另一边算。这样两种玩法才能共用同一套结算——互动剧本里你在司令部读报，兵棋推演里你直接点棋子，底下跑的是同一个引擎。

哑还要哑进编译器，不能只停在文档上。事件在关卡处被翻成报告，过了这道关，上层只拿得到报告。类型隔离如果能用 lint 拦住，就不该靠谁记得住约定：上层源码里出现事件类型，构建直接失败。《架构设计说明书 v1.1》的评审把这条写成规则，因为它不依赖自觉，也不给例外留口子。

最后是入口。脚本、命令行、图形界面，换的是方向盘，不是机制。只要它们都走同一条命令通道、读同一份报告，换哪一个都不该让前面的断言作废。反过来，如果机制开始跟着界面走，断言会一个个失效，最后没人说得清游戏本身有没有变。

契约的强度，最终由换桩检验，不由文档篇幅决定。谁想改这条线，先问一句：换掉一边，另一边还要不要改？答案是不用改，契约就还在；答案是要改，先改契约，再改实现。
