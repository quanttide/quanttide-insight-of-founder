# 系统契约与分层架构

## 1. 背景与问题

指挥部（决策层）与引擎（结算层）由不同团队独立开发。决策层负责判断“做什么”，结算层负责判断“做完之后发生了什么”。由于两侧最终必须协同运行，因此必须在开发前明确双方的通信协议与职责边界。

## 2. 契约定义

决策层向结算层下发命令（Command），结算层向决策层回传事件（Event）。除此之外，两侧不得访问对方的内部状态，也不得绕过约定接口直接修改对方数据。

命令的数据结构、事件的排序规则应在开发前确定。契约一旦确立，两侧均须在其自身边界内实现，不得以任何形式越过边界访问对方内部。

## 3. 契约验证：可替换性测试

文档层面的共识不足以证明契约有效。两侧可能对同一接口做出不同解读，而这类偏差往往要到集成阶段才会暴露。因此，契约必须通过可替换性测试进行验证。

### 步骤一：构建桩实现（Stub）

结算层先以桩实现替代真实逻辑，按预定义规则对命令返回固定事件序列；决策层同样以最简实现读取事件并结束一个回合。目标是先打通完整调用链路。

### 步骤二：单侧替换

保持一侧代码不变，将另一侧替换为真实实现，并验证系统能否继续正常运行。

- 若运行正常，说明被替换侧对另一侧不存在隐式依赖，契约边界成立；
- 若运行失败，说明两侧之间存在未纳入契约的隐含耦合，需回到接口定义层面修正，而非在实现层打补丁。

## 4. 设计原则

### 4.1 结算层职责单一

结算层应保持“无决策、无状态推断”的纯逻辑实现：

- 仅解析命令，并回传实际发生的结果；
- 不判断命令是否合理，不替决策层补充意图，也不根据上下文自行修正数据；
- 不引入对特定玩法或业务场景的硬编码分支。

结算层越接近纯函数式实现，两侧解耦越彻底。一旦结算层开始推断上层意图，不同玩法将产生分支依赖，最终演变为“一种玩法一套结算”。

### 4.2 编译时强制隔离

原始事件在关卡（Boundary）处转换为报告（Report）。越过该边界后，上层只能访问报告，不得直接触碰原始事件。

该约束通过编译期检查（类型系统或构建流程）强制生效：任何上层模块直接引用原始事件的代码，构建立即失败。此规则不设例外，也不依赖开发者自觉遵守。

### 4.3 入口层统一

脚本、命令行、UI 等外部入口统一接入同一条命令通道，并读取同一份报告。入口层仅负责输入适配，不包含任何结算逻辑。

若机制随界面变化而偏移，则新增按钮或改动交互时就会反向污染结算层，最终无法判断变更影响的是交互方式还是核心规则。

## 5. 结论

判断系统分层是否成功，不在于契约文档的页数或接口的详尽程度，而在于当某一组件被独立替换时，另一组件是否需要同步修改。

- 若无需修改，则契约有效，边界真实存在；
- 若必须联动调整，则应优先修正契约定义与边界划分，而非在代码层面用补丁掩盖耦合。
